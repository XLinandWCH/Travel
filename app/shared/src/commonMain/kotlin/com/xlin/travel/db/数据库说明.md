# 数据库层说明（`db` 包）

这一层负责把「聊天会话 + 每条消息」持久化到 SQLite，让应用重启后抽屉里还能看到历史对话，
并且让 AI 在新一轮对话时能读到之前的上下文。全部代码在 `commonMain`，三个平台共用同一套
SQL 与表结构，只有「数据库文件放哪、用什么驱动」由平台各自实现。

依赖：`androidx.sqlite`（2.7.1）+ `sqlite-bundled`（自带 SQLite so/dylib，不依赖系统版本）。
**没有**使用 Room / SQLDelight，都是手写 SQL 语句。

---

## 1. 文件职责一览

| 文件 | 角色 | 一句话说明 |
| --- | --- | --- |
| `ChatSchema.kt` | 建表脚本 | 定义库名 `travel_chat.db` 和全部 `CREATE TABLE / INDEX` 语句 |
| `ChatRecords.kt` | 数据模型 | `ConversationRecord` / `MessageRecord` 两张表的行映射类，以及 role、status 的取值常量 |
| `ChatDatabase.kt` | 连接管理 | 全应用共用**一个** SQLite 连接，用 `Mutex` 串行化访问；提供 `withConnection` / `withTransaction` |
| `ConversationDao.kt` | 会话表 SQL | `conversation` 表的增删查、按活跃时间排序、关键词搜索 |
| `MessageDao.kt` | 消息表 SQL | `message` 表的插入、按 `seq` 读取、更新内容/状态、删除 |
| `SettingDao.kt` | 设置表 SQL | `app_setting` 键值表的读写（主题偏好 / 登录缓存 / 模型配置缓存） |
| `ChatRepository.kt` | 统一入口 | 界面层**只依赖这个类**，把多个 DAO 组合成一个业务操作（如事务内追加消息并更新会话时间） |
| `DatabaseChatHistoryProvider.kt` | 桥接 Koog | 把数据库里的历史消息转换成 Koog Agent 的 `Message` 列表，供 `ChatMemory` 使用 |
| `PlatformDatabase.kt` | expect 声明 | `rememberChatDatabase()` / `currentEpochMillis()` / `randomUuid()` 的跨平台声明 |

平台实现（同一个 `rememberChatDatabase()` 的 actual）：

| 平台 | 文件 | 数据库位置 |
| --- | --- | --- |
| Android | `androidMain/.../db/DatabasePlatform.android.kt` | `context.getDatabasePath("travel_chat.db")`，即应用私有 databases 目录 |
| iOS | `iosMain/.../db/DatabasePlatform.ios.kt` | 沙盒 `Documents/travel/travel_chat.db`（目录自动创建） |
| JVM / 桌面 | `jvmMain/.../db/DatabasePlatform.jvm.kt` | `~/.travel/travel_chat.db` |

调用链：

```
App.kt
 └─ rememberChatDatabase()            // 平台 actual，创建 ChatDatabase
 └─ ChatRepository(database)          // 界面唯一的数据库入口
     ├─ ChatState                     // 发消息、落库、流式回写
     ├─ ChatHistoryState              // 抽屉里的历史列表与搜索
     ├─ SettingsScreen                // 主题偏好读写
     └─ DatabaseChatHistoryProvider   // 提供给 AI Agent 读上下文
```

## 2. 表结构

### conversation（一个会话一行）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | TEXT PK | UUID，同时作为 Koog `ChatMemory` 的 `sessionId` |
| `title` | TEXT | 会话标题，取用户第一句话的前 30 字 |
| `model` | TEXT? | 本轮使用的模型 ID（`Agents-A1`） |
| `system_prompt` | TEXT? | 创建会话时的系统提示词快照 |
| `created_at` / `updated_at` | INTEGER | 毫秒时间戳；抽屉按 `updated_at` 倒序排列 |

### message（一条消息一行）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | TEXT PK | UUID |
| `conversation_id` | TEXT | 外键 → `conversation.id`，`ON DELETE CASCADE`（删会话自动删消息，需要 `PRAGMA foreign_keys = ON`，已在开连接时执行） |
| `role` | TEXT | `user` / `assistant` / `system`（见 `MessageRoles`） |
| `content` | TEXT | 正文；AI 的思考内容不混在这里 |
| `reasoning` | TEXT | AI 思考（Reasoning）内容，界面用灰色显示 |
| `seq` | INTEGER | **会话内的顺序号，从 1 自增**。既是消息排序依据，也是「上下文分界线」的关键 |
| `status` | TEXT | `sending`（占位）/ `done` / `error`（见 `MessageStatuses`） |
| `prompt_tokens` / `completion_tokens` | INTEGER? | 预留：以后统计 token 用，目前写入为 NULL |
| `created_at` / `updated_at` | INTEGER | 毫秒时间戳 |

### app_setting（键值对，一行一个设置）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `key` | TEXT PK | 键名集中在 `SettingKeys`：`theme_preference`、`auth_token`、`auth_user`、`auth_avatar`、`model_config_cache` |
| `value` | TEXT | 一律用字符串存（主题存的是枚举名 `System` / `Dark` / `Light`） |

> `model_config_cache` 存的是服务端 `POST /api/model/config` 下发的模型配置 JSON
> （模型 id / apiKey / baseUrl / 系统提示词 / 温度 + 拉取时间），仅用于断网时兜底；
> 退出登录与注销账号时会连同 token 一起置空。

### 索引

- `idx_message_conv(conversation_id, seq)`：读某个会话的全部消息并按顺序排列时命中，避免全表扫。
- `idx_conversation_updated(updated_at DESC)`：抽屉列表按最后活跃时间倒序时命中。

## 3. 两个容易看不懂的机制

### 3.1 `seq` 与 `untilSeq`（上下文分界线）

`send()` 的执行顺序是：先算分界线 → 用户消息上屏并落库 → AI 占位消息落库 → 流式接收 → 回写 AI 内容。

```kotlin
val cutoff = repository.lastMessageSeq(conversationId)   // 本轮之前的最后一条 seq
repository.appendMessage(..., MessageRoles.User, ...)     // 本轮用户消息 seq = cutoff + 1
DatabaseChatHistoryProvider(repository, untilSeq = cutoff) // 只加载 seq <= cutoff 的历史
```

因为 Koog 会把 `chatStreaming(message = 用户输入)` 的这条输入**再拼一次**到上下文里，
如果历史加载也包含它，就会出现「同一句话在上下文中重复两遍」。用 `untilSeq` 把本轮用户消息
挡在历史之外即可。加载时截断（而不是删除）也保证了界面恢复时消息仍是完整的。

### 3.2 `status = sending` 的占位行

请求一发起就先插入一条 `content = ''` 的 assistant 记录，流式结束后用 `updateMessage` 回填
内容与状态（`done` / `error`）。好处是：进程中途被杀也不会丢掉这一轮的顺序位置。

两条读取路径都会过滤这种半成品：

- `ChatState.toChatMessage()`：`sending` 且正文与思考都为空 → 不显示（例如上次流式中途被杀）。
- `DatabaseChatHistoryProvider`：`sending` 或正文空白 → 不喂给模型。

### 3.3 建表为什么每次开连接都执行

所有语句都是 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`，在
`ChatDatabase.openConnection()` 里跑一遍即可，无需版本号与迁移脚本。
**代价**：以后给已有表加列时，`IF NOT EXISTS` 不会修改已存在的表，需要另外执行
`ALTER TABLE ... ADD COLUMN`（可 `runCatching` 忽略「列已存在」的报错）。

## 4. 并发与线程

- 全应用只有一个 `ChatDatabase` 实例、一个连接（`rememberChatDatabase()` 用 `remember` 缓存）。
- 每个操作都走 `withContext(Dispatchers.Default) { mutex.withLock { ... } }`，所以不会并发踩连接。
- `withTransaction` 用 `BEGIN IMMEDIATE / COMMIT / ROLLBACK`，`appendMessage` 在里面同时
  写 `message.seq` 和更新 `conversation.updated_at`，两者要么都成功要么都回滚。
- 界面侧所有数据库调用都套了 `runCatching`：数据库出错时聊天仍可继续，只是这一轮不落库。

---

## 5. 新增功能时该改哪里

1. 加列：先改 `ChatSchema.kt`（新库生效），再考虑老库的 `ALTER TABLE` 兼容。
2. 加字段映射：改 `ChatRecords.kt` + 对应 DAO 的 `Columns` / `insert` / `read`。
3. 加查询：SQL 写在对应的 `*Dao.kt`（`internal fun SQLiteConnection.xxx`），对外一律通过
   `ChatRepository` 暴露 suspend 函数，界面层不要直接触碰 DAO。
4. 加设置项：`SettingKeys` 里加常量名，用 `getSetting / setSetting` 读写。
